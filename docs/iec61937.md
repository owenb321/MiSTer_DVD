  (menus off, passthru on) sharpened the symptom: at **startup** the receiver did NOT lock
  — it flashed "Dolby Digital" a few times (header seen, no sustained data), and only a
  **chapter skip** kicked it into a solid lock; once locked, audio-track switches (DTS / DD
  2.0) played, but **too many switches** dropped it out again. When it works it is in sync

  (both fixed in `dvd/iec61937_wrap.sv`):
  1. **Startup real→null→real flap.** Sync gating was `sync_en = av_stc_anchored &
     ~av_freerun`. Before the STC anchored, `sync_en` was false so the producer **free-ran
     real AC-3 bursts** (receiver starts to acquire → "Dolby Digital"); then the anchor
     arrived, the demux parse-front sat ~0.5 s ahead of the STC, `hold_frame` went true and
     the producer switched to **Pc=0 null bursts** (receiver drops the stream it was
     acquiring); the hold then drained and real bursts resumed. Each cycle = one "flash." A
     chapter skip fixed it because `seek_ack` flushes + re-anchors cleanly (one null→real
     transition). **Fix — anchor-gate:** the wrapper now takes `sync_armed` (`~av_freerun`)
     and `stc_anchored` separately and **holds every codec frame (null bursts) while armed
     but not yet anchored**, so the receiver's first real burst is the start of the
     *sustained* post-anchor stream, not a pre-anchor spurt. Genlock Off still free-runs.
  2. **Burst-period jump on DTS / track switch.** Null/hold bursts were hardcoded to
     `PERIOD_AC3` (1536 samples), but a real **DTS** burst is 512 — so every hold beside a
     DTS stream (and every AC-3↔DTS switch) jumped the Pa/Pb repetition period 1536↔512,
     which drops receiver lock. **Fix — consistent period:** null/hold bursts now use the
     **active codec's period** (front frame's while queued/held, else a latched
     `cur_period`), so the grid period never changes across a hold.
  3. **★ ROUND 2 (2026-07-11): the anchor-gate REGRESSED it — pivot to PCM silence.** On
     HW the anchor-gate build was *worse*: 5.1 DD + DTS flapped more (only split-second
     audio), 2.0 / commentary locked better-but-flaky, and changing *tracks* helped more
     than *chapters*. Decisive tell: **AC-3 5.1 regressed even though the period fix never
     touches AC-3** (2.0 and 5.1 AC-3 are both 1536 samples) — so the regressor is purely
     the anchor-gate, whose only effect was to replace the old build's pre-anchor *real*
     bursts with ~1 s of **null bursts**. Conclusion: the receiver isn't tripping on the
     real→null *flap* — it **cannot acquire across non-PCM null bursts at all** (Pc=0 +
     non-PCM channel status = "compressed stream present, no data" = an ambiguous state no
     real source emits); the old build's early real bursts were *helping*. High-bitrate
     tracks flap more because they need a longer clean burst run to lock, so they're most
     sensitive to any silence gap. **Fix — do it the real-player way: PCM silence during
     the hold, not null bursts.** The hold/underflow path now emits **linear-PCM silence**
     (all-zero words, *no* Pa/Pb) with the **channel-status non-PCM bit CLEARED**; real
     data-bursts set it. A per-pair `nonpcm` flag rides the async FIFO (widened 32→33 bit)
     to `spdif_pass`, which **latches it once per 192-frame channel-status block** (frame 0)
     so the bit only flips on a clean block boundary. Net receiver behaviour = a real
     player: shows **PCM** during the pre-content hold, then a single clean **PCM→DD/DTS**
     switch when the bitstream starts (≤ one block ≈ 4 ms of transition lag — negligible,
     the receiver is still acquiring). The anchor-gate + consistent-period from round 1 are
     KEPT (they now gate PCM silence vs bitstream, which is correct); only the hold's
     *output* changed from null bursts → PCM silence.

### ⛔ ONE-SHOT HOLD GATE — TRIED 2026-08-31 AND REVERTED (do not retry)

**The hold is not a startup aligner. It is the CONTINUOUS pacing loop.** Making it
one-shot (apply until the first real burst since a flush, then stop) looked like
it should only remove redundant re-holds. On HW it produced **audio running ~1 s
AHEAD of video**, plus track-change flapping that had not been there before.

Why: the gate *is* how passthrough audio is paced against the video timeline —
the module header says so ("Holding fills the ring → engages the demux STD
backpressure, so the lead is bounded without dropping frames"). Disabling it
after the first burst removes A/V sync for passthrough entirely, and audio then
free-runs at ring-delivery rate, which leads the display by roughly the VBUF
depth.

★ **The corollary is the useful part: the hold/release chatter at startup is not
a bug, it is the controller working.** It is a bang-bang loop — hold, release,
hold, release — and that is *how* it bounds the lead. So any fix that tries to
stop the chattering stops the pacing. It measurably improved lock (optical went
from never locking to locking) precisely because it stopped pacing.

**Therefore the flap must be addressed at the CHANNEL-STATUS layer, not the hold
layer** — keep the bang-bang data pacing, but stop the non-PCM bit following it
once the stream is running, so the receiver sees a continuous non-PCM stream with
brief data gaps rather than repeated PCM↔non-PCM format changes. ⚠ Untested, and
it sits close to the round-1 failure mode above (non-PCM asserted with no data),
so it needs the same "locks at startup without a chapter skip" HW gate — the
difference being that round 1 asserted it for ~1 s BEFORE any content, where this
would only bridge gaps in an already-acquired stream.

## Why

The core decodes AC-3 and LPCM to PCM in fabric (`dvd/dvd_audio_decode.sv`), but
**DTS was dropped entirely** — there is no in-fabric DCA decoder and writing one is a
disproportionate from-scratch RTL project (`docs/audio.md`, CLAUDE.md audio decision).
The realistic way to make DTS (and AC-3) audible without decoding it in fabric is
**IEC 61937 passthrough**: wrap the *undecoded* elementary frames in IEC 61937 data-bursts
and send them as a bitstream for an AV receiver to decode. This is the documented "Path B"
in `docs/audio.md`. It requires an AV receiver — over optical S/PDIF, and **as of
2026-08-30 also over HDMI** (`docs/hdmi_bitstream.md`), so the Digital I/O board is no
longer required. On a plain TV that cannot decode AC-3/DTS it stays inaudible; for that,
use Decode mode, which is unchanged.

Raw AC-3/DTS frames already reach `dvd/audio_ring.sv` (ps_demux strips the
private_stream_1 sub-header; the AC-3 reframer makes AC-3 frame-granular). The work is a
burst formatter + biphase encoder + a mode toggle + pin wiring.

## User controls

- **`O6` Audio Out — Decode HDMI (default) / Passthru SPDIF.** Passthru makes
  `iec61937_wrap` the ring's reader, mutes the HDMI PCM (`AUDIO_L/R = 0`), and drives the
  S/PDIF pin with the 61937 bitstream. Decode mode is bit-for-bit the previous behaviour.
- **`O7` SPDIF Byte Order — Normal / Swap.** Flips the payload byte→word packing *live*.
  Payload byte order is the classic "receiver recognises the format but plays static"
  gotcha, and each rebuild is a long Quartus compile, so it is a runtime toggle rather than
  a rebuild. If the receiver shows "Dolby D"/"DTS" but hisses, flip this.

## Architecture

```
audio_ring (clk_sys 27 MHz)                         clk_audio (24.576 MHz)
┌────────────────────────────┐    iec_dcfifo32   ┌──────────────────────────┐
│ iec61937_wrap producer FSM │  32-bit {R,L}     │ ÷4 → 6.144 MHz bit CE     │
│  assemble the 61937 word    │──── pairs ───────▶│ spdif_pass encoder        │─▶ SPDIF_PASS
│  stream: Pa Pb Pc Pd payload│    (async FIFO,   │ (IEC 60958 biphase-mark,  │   │
│  + zero-pad to burst period │     gray ptrs)    │  non-PCM channel status)  │   ▼
└────────────────────────────┘                   └──────────────────────────┘  sys_top mux
```

Files:
- **`dvd/spdif_pass.sv`** — a copy of the framework's `sys/spdif.v` (Ultra-Embedded IEC
  60958 biphase-mark encoder) with **one** functional change: the channel-status
  *non-linear-PCM* bit (byte 0, bit 1 = audio-block frame index 1) is asserted so the
  receiver treats each subframe payload as a compressed data-burst, not PCM. Kept as a
  separate module so `sys/spdif.v` (the normal PCM path) is untouched.
- **`dvd/iec61937_wrap.sv`** — the burst formatter + an inline gray-code async FIFO
  (`iec_dcfifo32`) + the CE generator + the `spdif_pass` instance.

### Burst format (`iec61937_wrap`)

The producer (in `clk_sys`, alongside the ring — no CDC on the ring interface) emits a
stream of 16-bit **words** per burst:

| word | value |
|------|-------|
| 0 | Pa = `0xF872` |
| 1 | Pb = `0x4E1F` |
| 2 | Pc = `0x0001` (AC-3) / `0x000B` (DTS) |
| 3 | Pd = payload length in **bits** (`frame_len * 8`) |
| 4.. | payload bytes, packed two per word (`byte_swap` selects the order) |
| rest | `0x0000` zero-pad |

That layout is for a **real** data-burst. A HOLD/underflow burst instead emits all-zero
words (no Pa/Pb) tagged as **linear PCM** (the per-pair `nonpcm` flag = 0), i.e. genuine PCM
silence — see the status block "ROUND 2".

Total words per burst = `period * 2`, where `period` is the codec frame's sample count
(AC-3 = 1536, DTS = the frame's real count, 512 by default until the reframer supplies it).
Words are packed two-per-pair (low/first word = the LEFT subframe) and handed across the
async FIFO to the encoder. Each pair also carries a 33rd `nonpcm` bit (1 = data-burst, 0 =
PCM silence) that `spdif_pass` latches once per channel-status block to drive the non-PCM
channel-status bit.

### Self-pacing

One 61937 burst carries exactly one codec frame, zero-padded to the codec's burst period
in stereo sample pairs. The `spdif_pass` encoder drains one pair per 48 kHz sample, so
emitting exactly `period` pairs per frame makes the **average word rate real-time**; the
async FIFO only smooths CDC jitter. Because the producer reads the ring at that real-time
rate, the ring's existing `almost_full` STD backpressure applies in Passthru exactly as in
Decode. On ring underflow (or a held frame — see A/V sync) the producer emits **linear-PCM
silence** (all-zero words, no Pa/Pb, channel-status non-PCM bit cleared) — never garbage,
and never a Pc=0 non-PCM null burst (HW showed receivers can't acquire across those; see the
status block "ROUND 2").

### A/V sync (slave passthrough audio to the video STC)

Passthrough originally free-ran: it emitted each ring frame's burst as soon as the frame
arrived (the demux *parse* front), while the decoder's ~1 s VBUF means video is displayed
~1 s later — so audio ran ~1 s ahead of video (HW round 1). The same VBUF-lead the decode
path's `av_sync` compensates for, uncompensated on passthrough.

Fix: `iec61937_wrap` **holds** a not-yet-due frame — emitting PCM silence, not popping it —
until the video STC reaches it, using the exact compare `dvd_audio_decode` uses:
`head_delta = signed(stc) − signed(frame_pts) − av_ofs`, due when `≥ 0`. Reuses av_sync's
`av_stc` + the `O[23:21]` A/V Offset (`av_ofs`), gated by `sync_armed = ~av_freerun` +
`stc_anchored = av_stc_anchored` (holds until anchored, then until due). Holding fills the ring, which engages the demux STD
backpressure, bounding the lead without dropping frames. Frames without a PTS (or genlock
Off) free-run for continuity. Sim: `iec61937_wrap_tb` TEST 6 (held while `stc<pts`,
released when `stc≥pts`).

### Clocking

`CLK_AUDIO` = 24.576 MHz (framework `pll_audio`), previously unused inside `emu`. The
S/PDIF bit rate for 48 kHz is `48000 × 32 × 2 × 2 = 6.144 MHz = 24.576 MHz ÷ 4` — a clean
integer divide (`ce_cnt`), matching `sys/audio_out.v`'s `mclk_ce`. A reset synchronizer
(async assert / sync deassert) crosses `aud_rst_n` into `clk_audio`.

## Wiring

- **`dvd/emu.sv`:** `pass_mode = status[6]`, `pass_bswap = status[7]`. Ring read-side
  arbitration muxes `aud_ring_ready`/`aud_frame_pop` between `dvd_audio_decode` (Decode)
  and `iec61937_wrap` (Passthru); the decoder is also disabled and HDMI PCM muted in
  Passthru. New emu outputs `SPDIF_PASS` (bitstream) + `SPDIF_PASS_EN` (= pass_mode).
- **`sys/sys_top.v`:** a deliberate, minimal edit (the framework's `audio_out` only makes
  a PCM `spdif`; passthrough requires driving the pin directly). `spdif_out =
  spdif_pass_en ? spdif_pass : spdif` replaces `spdif` in the `AUDIO_SPDIF` and
  `SDCD_SPDIF` pin assigns — the PCM path is bit-identical when disabled. Drives both
  optical destinations (Digital board `AUDIO_SPDIF`, Analog board combo `SDCD_SPDIF`).

## Hi-res LPCM over S/PDIF (PLANNED — sidestep the 16-bit HDMI cap)

**Status: 📋 design only, no RTL. Implement when a 96 kHz/24-bit LPCM disc is in hand to
verify against** (per the project's "don't build without a test vehicle" rule). Motivating
gap: the local library has **no LPCM disc at all** (`docs/test_disc_shopping_list.md` Tier 1),
and 24-bit/96 kHz LPCM is the deferred `lpcm_unpack` case.

### The idea

Route **hi-res LPCM straight out S/PDIF as linear PCM** instead of decoding+downconverting it
for HDMI. This is exactly what a real DVD player does with hi-res LPCM, and it dodges a *hard*
limit: the MiSTer core→framework audio interface (`AUDIO_L/R`) is **16-bit** and (from the
core's samples) 48 kHz, so the HDMI path **cannot** carry 24-bit — a 24-bit source must be
truncated. **S/PDIF sidesteps that**: `spdif_pass` drives the optical pin *directly* with its
own biphase encoder (bypassing `AUDIO_L/R`), and the **IEC 60958 subframe carries 24 bits of
audio natively** → 24-bit LPCM goes out **bit-perfect**, no truncation, no resample DSP.

**"Sidestep decoding" is ~true but not literal:** LPCM is uncompressed, so there's no decode —
but the samples still need **unpacking** (deinterleave the big-endian 20/24-bit samples + read
the sub-header). What's skipped is the *lossy* part (24→16 truncation, 96→48 resample). The
unpack itself is trivial and lossless.

### What already exists (reuse, don't rebuild)

The PCM S/PDIF path is **already live** — the re-lock fix (PR fj#110) emits real **linear-PCM
silence** during A/V holds via the per-pair `nonpcm` flag (bit [32] of the FIFO word) →
`spdif_pass.nonpcm_i` clears the IEC 60958 non-PCM channel-status bit. So "send PCM out
S/PDIF" is a solved, HW-confirmed path; the AC-3/DTS data-burst is just its `nonpcm=1` sibling.
The clock is already right too: `CLK_AUDIO` = 24.576 MHz, 48 kHz S/PDIF = 6.144 MHz = ÷4;
**96 kHz = 12.288 MHz = ÷2 of the same `pll_audio`** — a clean divide, no new PLL.

### Concrete work (moderate, surgical)

1. **`ps_demux`** — stop discarding LPCM sub-header **byte 4** (word length bits 6-7 =
   16/20/24, sample freq bits 4-5 = 48/96 kHz, channels bits 0-2); expose it so the format is
   detectable (today it's stripped, so a 96/24 disc plays **garbled**, not just downmixed).
2. **`spdif_pass`** — widen the sample path **16→24-bit** (`audio_sample_q`/`sample_buf_q` and
   the subframe fill; the 24-bit field already exists in the subframe) and set the
   **channel-status word-length + sample-frequency bits** so the receiver locks at the right
   rate/depth.
3. **LPCM→S/PDIF PCM feed** — a sibling to the AC-3/DTS burst path in `iec61937_wrap`: unpack
   LPCM to 24-bit `{L,R}` pairs and push them as **PCM** (`nonpcm=0`) into the FIFO (widen the
   33-bit word to carry 24-bit samples). No 61937 burst wrapping — raw PCM subframes.
4. **96 kHz mode** — run the `spdif_pass` consumer CE at 12.288 MHz (÷2) + channel-status Fs =
   96 k, selected from the sub-header rate bit.

### Scope the target by what's guaranteed vs hardware-gated

- **24-bit / 48 kHz = the guaranteed win.** Works on essentially all S/PDIF gear, and it fixes
  the *more common* gap (24-bit at 48 k). Do this first.
- **24-bit / 96 kHz = a hardware-permitting stretch.** Needs the board's TOSLINK transmitter
  **and** the receiver to clock the doubled bit rate (12.288 MHz); some do, cheap optical
  modules don't. Verify empirically with the disc + receiver in front of you.

### The two caveats that bound it

- **Receiver-only feature.** Audio leaves to an AV receiver/DAC — optical/coax, or HDMI
  since 2026-08-30 (`docs/hdmi_bitstream.md`). Either way a plain TV that cannot decode
  AC-3/DTS gets nothing from this path, so keep a **16/48 HDMI LPCM fallback** (the existing
  `lpcm_unpack` Decode path, truncated) so those users aren't silent. ⚠ Note the hi-res-LPCM
  plan below is S/PDIF-only: the HDMI leg carries *compressed* bursts, and multichannel or
  24-bit LPCM cannot ride it (see `docs/hdmi_bitstream.md` §7).
- **A `SetSTN`/track-switch to an LPCM track must route it as PCM S/PDIF**, mirroring the
  AC-3/DTS mode switch (channel-status PCM↔non-PCM already handled per-block).

`docs/audio.md` "Path B".

## Known limitations / follow-ups

- **✅ Re-lock / startup lock — DONE, HW-CONFIRMED (PR fj#110,
  `feature/spdif-passthrough-relock`).** Round 1 (anchor-gate + consistent burst period)
  REGRESSED on HW, which proved the receiver can't acquire across Pc=0 non-PCM null bursts
  at all. Round 2 fix = **PCM silence during holds** (dynamic non-PCM channel-status bit,
  per-pair flag across the FIFO), keeping the round-1 anchor-gate/period. Confirmed on the
  real receiver (T2 ISO): passthrough locks at startup and holds through audio-track
  switching, DD + DTS both decode. Full write-up in the status block at the top of this
  file. *(Should a future disc ever regress: untried levers are (a) an explicit brief
  mute/gate of `iec61937_wrap`/`spdif_pass` at the audio-switch point — the Phase-10
  audio-switch reset reaches the wrapper only via `aud_rst_n`; (b) the DTS burst-period/fit
  for a 1509 kbps core DTS track ≈ 2048 B, which fills the whole 512-sample burst — snoop
  `NBLKS` and/or bump the burst period.)*
- Needs an AV receiver that decodes AC-3/DTS — over optical, or over HDMI since 2026-08-30
  (`docs/hdmi_bitstream.md`). Inaudible on a plain TV that decodes neither. (PCM in Decode
  mode works on anything, as before.)
- **DTS burst period is fixed at 512 samples** (`PERIOD_DTS`). Correct for the common DVD
  DTS case (NBLKS=15, verified on the T2 track and HW-confirmed working), but a
  1024-sample-frame DTS stream would drift the receiver buffer. **Refinement:** snoop
  `NBLKS` from the frame header (`samples=(NBLKS+1)*32`) during payload read and set
  `frame_samples` per frame. Deferred; add if a 1024-sample disc shows drift.
- LPCM/unknown tracks in Passthru emit silence (guarded — use Decode mode for LPCM).
- Core DTS only (48 kHz, ≤16-bit S/PDIF) — no DTS-HD / 96 kHz / >16-bit.
- Pd is 16-bit; fine for AC-3 (≤3840 B) and core DTS, would overflow for very large
  frames (not encountered).
- ✅ RESOLVED (M19 area pass, PR fj#109): the build used to be clk_dec timing-marginal at
  91% ALM. The AC-3 area pass (`docs/ac3_decoder_architecture.md` §4.11) dropped the
  design to 86% ALM / 81% DSP; SEED 7 now routes with real margin (clk_dec 86.07 MHz
  @100C / 88.32 MHz @-40C, both above the 81 MHz gate) — no longer a fringe-lottery build.
